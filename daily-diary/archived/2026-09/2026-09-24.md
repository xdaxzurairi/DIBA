## 2026-09-24 (Sesi Panjang) - eWorks: Security Audit + Fix sign_arahan_kerja.php & save_signature.php

### Session summary
Semak keselamatan `sign_arahan_kerja.php` (portal_kontraktor eWorks) atas permintaan Abam — jumpa IDOR, bypass role tandatangan, tiada CSRF, dan fail-open pada semakan penyelia. Semasa uji end-to-end di browser sebenar, jumpa juga bug produksi tak berkaitan (SQL crash, gambar broken, dan page kosong `ERR_CONTENT_DECODING_FAILED`). Semua dibaiki, diuji terhadap DB & browser sebenar, commit & push ke `origin/master`.

### Key decisions
- IDOR fix: sahkan `wr_id` memang ditugaskan kepada `kontraktor_cf_id` sesi (query `wrcf` dengan `CAST(...AS VARCHAR(MAX))` untuk elak collation/type mismatch) — diterapkan di kedua-dua `sign_arahan_kerja.php` (paparan) dan `api/save_signature.php` (API)
- Role bypass fix: sesi kontraktor cuma boleh POST role `pengadu`/`kontraktor` ke API; `siasatan`/`pengurusan` (tandatangan staf) ditolak walaupun API dipanggil terus
- Isu #3 (fail-open penyelia bila tiada supervisor direkod): kekalkan behavior sedia ada (mana-mana staf boleh sahkan) atas keputusan Abam — data sebenar 97% wr_id ada supervisor direkod, 3% tiada; deny-by-default akan kunci kes tu
- CSRF: guna class `CSRF` sedia ada (`includes/csrf.php`), token dihantar dalam payload JSON `simpan()` dan disahkan di `save_signature.php`
- Validasi tarikh esign (siasatan & pengurusan) yang asalnya cuma client-side JS — direplikasi penuh di server (`api/save_signature.php`) supaya tak boleh dipintas dengan panggilan API terus
- **Bug produksi dijumpai semasa ujian** (bukan diminta, tapi dibaiki serentak):
  - SQL crash: `cf.in_house = '1' OR cf.in_house = '1.0'` — column smallint tak boleh convert `'1.0'`, sentiasa throw fatal error bila cuba sign "Pengurusan Fasiliti" → tukar ke `cf.in_house = 1`
  - `ERR_CONTENT_DECODING_FAILED` (page kosong/blank total): `config/performance.php` guna `ob_start('ob_gzhandler')` DAN `ini_set('zlib.output_compression','On')` serentak — double gzip compression, konflik yang didokumenkan rasmi dalam manual PHP. Buang blok `zlib.output_compression` yang redundant
  - Gambar kerosakan broken untuk aduan pre-MinIO (fail lokal `uploads/wr/` kosong di server ni) — tambah fallback UI "Gambar tidak tersedia" bila `<img onerror>`
  - `sw.js`: `cache.put(request, ...)` guna objek Request navigate-mode terus — anti-pattern SW yang dikenali; tukar ke `cache.put(request.url, ...)`, naik versi cache ke v2.1.1
- Set kata laluan ujian untuk akaun kontraktor sedia ada (`ew_portal_kontraktor`, cf_id=JR0041178-W) untuk uji flow — akaun test/gmail, bukan akaun staf sebenar
- Elak reset kata laluan akaun staf sebenar (afm_users, cf_id=211378 Amir B Miskon) — Abam sahkan itu akaun sendiri, log masuk terus guna kredensial sedia ada

### Fail yang diubah
- `sign_arahan_kerja.php` — semakan pemilikan wr_id (IDOR), generate & embed CSRF token, guna `json_encode` bukan `addslashes` untuk `_wrId`/`_csrfToken` (tutup XSS reflected minor sekali)
- `api/save_signature.php` — semakan pemilikan wr_id, sekatan role ikut jenis sesi, validasi CSRF token, validasi tarikh siasatan/pengurusan penuh di server, fix SQL `in_house` type
- `config/performance.php` — buang `zlib.output_compression` (double gzip conflict)
- `sw.js` — `cache.put()` guna `request.url`, naik versi cache v2.1.0 → v2.1.1
- `portal_kerja.php` — papar banner alert untuk `?error=akses_ditolak`
- `includes/paparan_lengkap_print_body.php` — fallback "Gambar tidak tersedia" bila fail foto hilang

### Ujian yang dijalankan
- Query SQL ownership logic terhadap DB produksi sebenar (allow/deny kes sebenar)
- Ujian logik role-filter (8 kombinasi) & CSRF (token betul/salah/kosong) — semua lulus

- Validasi tarikh server-side diuji terhadap 6 kes (data sebenar `wr_id=1295563`) — semua padan jangkaan
- Root-cause `ERR_CONTENT_DECODING_FAILED` disahkan terus dari Console DevTools Abam (bukan teori) selepas siasatan panjang (SW, CSP, network — semua disingkir dulu sebelum jumpa punca sebenar)

## 2026-09-24 (Sesi eWorks) - Fix Threshold & Label Tahap 4 — Laporan Action Time Ikut Tahap (menu 6f)

### Session summary
Abam lapor (dengan screenshot perbandingan) nombor "Tahap 4 (7 Hari) - Tempoh Siap" pada laporan `lap_actiontime_all_kampus_tahap.php` (menu 6f) salah. Siasatan jumpa punca: query SQL guna ambang `action_period <= 72` jam untuk kategori "7 HARI" — sepatutnya `<= 168` jam (7×24). Bug ni sebenarnya diwarisi drpd `lap_tahap_kerosakan.php` (4d) semasa CR 2026-09-14, yang masa tu sengaja "disetujui" supaya nombor 6f sepadan dgn 4d. Abam sekarang sahkan itu salah dan minta betulkan — tapi skop 6f sahaja (4d/backlog/negeri sengaja tak disentuh). Turut dikemaskini: format label baris "Tempoh Siap" ikut rujukan gambar Abam. Diuji live di dev, disahkan, push ke prod.

### Key decisions
- Fix threshold Tahap 4 (7 HARI): `action_period <= 72` → `<= 168` jam — **HANYA** dalam `lap_actiontime_all_kampus_tahap.php` (arahan eksplisit Abam: "betulkan 6f shj")
- Bug sumber asal (pattern sama `b.period='7 HARI' and a.action_period <= 72`) turut wujud di `lap_tahap_kerosakan.php` (4d), `lap_tahap_kerosakan_backlog.php`, `lap_tahap_kerosakan_negeri.php` — **SENGAJA tak dibaiki**, di luar skop CR ni
- Bukti ia bug (bukan reka bentuk): fungsi `getDemeritPoint()` dlm fail yg sama guna sempadan `168` jam utk kes '7 HARI' — mengesahkan 168 jam (bukan 72) ialah takrifan sebenar sistem
- Label baris "Tempoh Siap" ditukar drpd format `TAHAP N (X) - TEMPOH SIAP` kepada `TAHAP N - TEMPOH SIAP ≤ X` ikut rujukan gambar Abam (baris "... - SIAP" di atasnya sengaja tak disentuh)
- Ini membalikkan keputusan CR 2026-09-14 yang sengaja meniru quirk 72 jam drpd 4d "supaya konsisten" — keputusan tu kini digantikan atas arahan Abam

### Fail yang diubah
