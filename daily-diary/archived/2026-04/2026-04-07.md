## 12:30 — form_aduan_inisiatif: AJAX Restore on Kembali Edit (Round 5)

**Summary**: Dropdowns masih "Sila Pilih" selepas klik "Kembali untuk Edit" — walaupun PHP render `selected` attributes. Fix: tambah AJAX waterfall restore dalam `returnToEditForm()`.

**Root Cause**: PHP memang render `<option selected>` dgn betul, tapi browser tidak honour `selected` attributes pada hidden form elements yang dipapar semula. Beberapa dropdown (Negeri, Kampus, Blok, Ruang, Masalah) hilang nilai manakala Bangunan, Aras, Seksyen, Elemen kekal.

**Fix (3 changes)**:
1. `$prefill_data = $preview_data` (dari fix sebelum) → `prefillDraft` JS object kini ada semua preview values
2. `returnToEditForm()` → async, panggil `await restoreDraftViaAjax(prefillDraft)` sebelum apply UI state
3. `restoreDraftViaAjax()` → buang guard `!hasPrefillDraft` supaya boleh dipanggil dari mana-mana

**Impak**: Bila user klik "Kembali untuk Edit", SEMUA dropdown direbuild via AJAX + values ditetapkan secara eksplisit. Tiada lagi dependency pada PHP `selected` attributes atau browser behaviour.

**Files Changed**: form_aduan_inisiatif.php (3 changes)

## 13:45 — Notification System: Mark Read & Auto-Remove from List

**Summary**: Implemented notification disappear on read feature. When user clicks complaint in notification list, it's now marked as read AND removes from senarai immediately (no polling wait). On page refresh, notification stays gone (persisted to DB).

**Key Decisions**:
1. Backend filter: Add `AND n.is_read = 0` to `get_notifications.php` WHERE clause — only serve unread notifications
2. Frontend immediate removal: Modify `markAsRead()` to `.filter()` remove item from array instead of just marking `is_read=true`
3. Re-render UI immediately selepas removal — no delay, no extra API call

**Root Cause of Current Issue**: 
- API returned ALL notifications (read + unread) without filter
- Frontend updated local state but didn't remove from list
- User clicked notification → marked read in DB → but stayed in UI until polling (30s delay)

**Files Changed**:
- `api/get_notifications.php` (Line 169): Added `AND n.is_read = 0` filter in WHERE clause
- `assets/js/notifications-list.js` (Line 407-430): Updated `markAsRead(wrId)` function:
  - Remove line with `.find()` and `notif.is_read = true`
  - Replace with `.filter(n => n.wr_id !== wrId)` to remove from array
  - Keep `renderNotifications()` call for immediate UI update
  - Badge updates via `updateBadge()` with server response

**Verification**:
- ✓ Backend fallback logic (seed + ULTIMATE fallback) — all create `is_read=0` records, consistent with filter
- ✓ Click handler unchanged — navigates after `markAsRead()` API call (async, non-blocking)
- ✓ On refresh: notification gone (DB persisted) because query filters `is_read=1`

**Flow After Fix**:
1. User clicks complaint in notification list
2. `markAsRead(wrId)` fires → POST to `api/mark_notification_read.php` → DB updated to `is_read=1`
3. On success: item removed from `this.notifications` array, UI re-rendered (notification disappears)
4. Navigation triggered in parallel
5. On refresh: API query shows only `is_read=0` records → notification absent from list

**Follow-ups**: 
- Monitor for any edge cases with polling (30s) — notification might reappear if count sync issue
- Consider dismissal UX feedback (toast message or animation)
